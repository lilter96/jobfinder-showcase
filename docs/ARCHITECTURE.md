# JobFinder — архитектура

Персональная система поиска работы: собирает вакансии из hh.ru / rabota.by / Хабр Карьеры / ~70 Telegram-каналов и чатов / Threads,
отсекает неподходящее детерминированными правилами, оценивает остальное LLM относительно резюме, сама откликается на hh выше
порога, остальное присылает в Telegram-бот на одобрение, пишет и публикует комментарии в Threads (по `policy.engagement.AutoPublish`, иначе после одобрения)
и собирает базу компаний с открытыми .NET-вакансиями. Один пользователь, локальный `docker compose`.

## 1. Решения и почему

Исполняемая миграция архитектуры и её незакрытые условия описаны в `docs/REFACTORING.md`. Предпочтения автоматизации, LLM и поиска
живут в типизированных версионируемых политиках PostgreSQL (`policy.automation`, `policy.llm`, `policy.search`, `policy.engagement`), а не в независимо
переопределяемых runtime-файлах. Старые Options импортируются из эффективной конфигурации один раз; дальше они только совместимый
bootstrap. История, проверка ожидаемой версии и уведомление публикуются атомарно. Детали: `docs/LLM-TASKS.md`, `docs/SEARCH-POLICY.md`.

| Вопрос | Решение | Почему |
|---|---|---|
| Стек | .NET 10, один процесс ASP.NET Core (Blazor Server + hosted services) + PostgreSQL | Один деплой, одна БД, воркеры и UI делят DI и `DbContext`. |
| Durable execution | Wolverine 6.41.0, EF outbox и нативный PostgreSQL transport | Результат этапа и следующая команда сохраняются атомарно; перенесены ручные hh-ссылки, обработка постов Telegram/Threads, оценка вакансий, письма, резюме, комментарии, доставка работодателям и подготовка интервью. Уведомления имеют нативный per-effect executor и handoff из workflow; обычные producers, legacy и итоговые release-проверки ещё требуют миграции. Без нового broker или отдельного сервиса. |
| hh.ru / rabota.by | Публичные страницы, JSON из `<template id="HH-Lux-InitialState">`; отклик — Playwright под сохранённой сессией | API для соискателей закрыт (дек. 2025), `GET /vacancies` без авторизации — 403 (апр. 2026). Встроенный JSON стабильнее вёрстки. У обоих сайтов общий движок и общие id вакансий → один источник `HeadHunter`, хост хранится отдельно. |
| Хабр Карьера | `career.habr.com/api/frontend/vacancies` (JSON) + JSON-LD `JobPosting` со страницы вакансии | Без логина, структурировано. |
| Telegram | MTProto user-аккаунт (WTelegramClient), апдейты в реальном времени + догонка истории по `last_message_id` | Боты не видят чужие каналы; подписка + mute + архив + папка «Jobs» — без поллинга и FLOOD_WAIT. |
| Threads | `IThreadsClient`: официальный API (если есть токен с `threads_keyword_search`), иначе Playwright | App Review у Meta пока нет; переключение — флагом в конфиге. |
| LLM | OpenRouter, своя ротация моделей по назначению (`Extract`/`Score`/`Letter`/`Comment`), circuit breaker на модель, JSON Schema structured output с валидацией | Дёшево (GPT-6 Luna ≈ $0.05/$0.25 за 1M), падение модели или провайдера не останавливает конвейер. |
| Автоотклик | Скор ≥ 80 и отклик возможен без теста → авто (≤ 25/день); 60–79 → карточка в боте; < 60 → только дашборд | Ответы пользователя. Лимит hh ≈ 200/день, наш потолок сильно ниже. |
| Нейрокомментинг | Native draft/check/rewrite → первый чистый вариант либо выбор; отдельные подготовка/публикация, журнал попыток и сохранённый pacing. Неизвестный исход — только ручная сверка, без fallback/автоповтора. Live acceptance и production cutover ещё не закрыты | Выбор пользователя (2026-09-28): полностью автоматически; лимиты в день и на автора ограничивают частоту. |
| Уведомления | Native outbox/workflow → Telegram-бот: важное сразу, остальное в дайджесте 09:00 и 19:00 (Минск) | Текст, документ и редактирование имеют отдельные попытки/receipts; неизвестный исход не повторяется. Старые Pending не считаются доказанно неотправленными, даже при Attempts=0. |

## 2. Процессы и контейнеры

```
docker compose
├── postgres:17            volume pgdata
└── app (JobFinder.App)    127.0.0.1:8080 → Blazor dashboard
    ├── Collectors      HhSearchJob, HabrSearchJob, ThreadsSearchJob, CompanyCollectorJob
    ├── Durable Discovery   ReadHhLink → LinkHhContacts; ProcessPost: read → extract → verify → publish; legacy-воркеры только импортируют
    ├── Durable resume      DraftResume → PrintResume → ReviewResume → FinishResume; ResumeWorker только публикует
    ├── Durable Hiring      PrepareEmployerMessage → DispatchEmployerMessage; переписка, outreach и hh CLI через общий gateway
    ├── TelegramListener   WTelegramClient: updates + catch-up + ChannelSync (join/mute/archive/folder)
    ├── Pipeline workers   PostExtractor → ingest + CaptureVacancyAssessment атомарно; VacancyWorker импортирует legacy New
    ├── Durable capture    подготовка snapshot → assessment + ScoreVacancy атомарно, без LLM в ingest
    ├── Durable assessment ScoreVacancy → PrepareVacancyLetter → FinishVacancyAssessment (score → letter → decision/card)
    ├── ApplyWorker        Playwright (hh.ru / rabota.by)
    ├── Durable Engagement PrepareCommentSource → DraftComment/CheckComment → source/card → PrepareCommentDelivery → DispatchCommentDelivery
    ├── Bot                Telegram.Bot long polling + native NotificationDeliveryWorkflow; NotificationDispatcher только импортирует legacy
    ├── Durable controls   PostgreSQL inbox/cursor → отдельная bot_controls queue → сохранённый claim → source handlers; сбой не повторяется вслепую
    └── volumes            ./data (PDF резюме и пакетов интервью, скриншоты, отладка), ./config, ./profile (resume.pdf), ./prompts
```

Всё состояние живёт в БД: статусы конвейера (legacy-воркеры забирают работу запросом `WHERE status = …` батчами; ручные hh-ссылки —
через Wolverine/PostgreSQL и `hh_link_requests` с сохраняемыми этапами Reading/Linking), профиль и факты
кандидата, логины браузеров, сессия MTProto и позиция апдейтов Telegram, ключи дашборда. После прерывания отправки отклика `Sending`
переходит в `OutcomeUnknown`: повтор остановлен до сверки доставки. PostgreSQL не может атомарно подтвердить внешний SMTP/Telegram/
браузерный эффект. Ни одно состояние не живёт в файле — сервер на хосте, CLI в контейнере и бэкап видят одно и то же.

```

Threads post ─┴→ raw_posts ─ prefilter ─ PostEnricher ─ LLM Extract ─┐      │                        │
   text links, buttons) (regex)  (pages the post links to,  (post +   ├→ vacancies (New) ←─────┴─ Habr JSON
                                  contacts, JobPosting)     pages)   │
                                                      │
          VacancyProcessor:  dedup/merge → HardFilter → LLM Score (+ salary adj) → DecisionPolicy
                                                                                    ├ AutoApply  → letter → applications(Pending) → ApplyWorker
                                                                                    ├ Approval   → letter → bot card [Отправить|Изменить|Пропустить]

```

### 3.1 Дедупликация
1. Одинаковый `(source, external_id)` — upsert источника (unique index).
2. Ссылка `hh.ru|rabota.by/vacancy/{id}` в посте Telegram/Threads → пост привязывается к hh-вакансии (если её нет — дотягиваем).
3. Иначе отпечаток `norm(company) + sorted(norm(title tokens))` в окне 30 дней → новая запись `vacancy_sources` у существующей вакансии.

Ручные hh-ссылки из UI, бота и `--add-vacancy` объединяются одним Discovery owner по активному hh ID. Контакты и команда сохраняются
в одной транзакции; после рестарта Linking не повторяет чтение. Сбой после ingest находит существующий источник, а не читает HTTP
страницу заново. Пауза источника становится нативной отложенной командой; старый HhLinksJob больше не исполняет этот поток.
Сервер подтверждает владение и применяет миграции/проверяет политики до старта listener; CLI только публикует в уже подготовленную
БД, не запускает MTProto/бота и не захватывает серверный lock. Подробности и ограничения: `docs/WOLVERINE.md`.

### 3.1a Ссылки поста, страницы и контакты
- **Захват.** У сообщения Telegram текст — не всё: ссылка часто спрятана под словом («Откликнуться» → URL), есть кнопки-ссылки и
  упоминания людей без @username. `TelegramLinks` берёт их из entities и `reply_markup` (смещения — UTF-16, как в .NET) в
  `raw_posts.links` (jsonb). Ссылка на hh — в тексте или спрятанная — ведёт пост на структурный путь hh (п. 3.1).
- **Страницы** (`VacancyCrawler`): ссылки поста читаются в ширину, глубина 2 (со страницы — только «подробнее / откликнуться» того же
  сайта или ссылка с площадки на сайт работодателя), не больше 6 страниц и 90 с на пост, каждая страница один раз (канонический URL без
  utm_*), запрос — как в ссылке (хост не меняется: `simbirsoft.com` и `www.simbirsoft.com` — разные серверы). Всё через `PoliteHttp`;
  не-HTML и страницы больше 4 МБ не качаются; ошибка страницы (404, TLS, блокировка, «404» с кодом 200) — строка в отчёте, не сбой поста.
  Пост Telegram по ссылке читается через публичный embed, Google Doc — как текстовый экспорт; страница, почти пустая без скриптов
  (Gatsby/React), рисуется headless-браузером (`BrowserSessions.RenderAsync`, без сессии, без картинок).
- **Разбор страницы** (`PageReader`): AngleSharp (HTML5-парсер) + SmartReader (Mozilla Readability) для основного текста; schema.org
  `JobPosting` из JSON-LD — зарплата, компания, удалёнка (его `description` не всегда текст — он запасной); шапка/подвал/меню — не
  контент; у известных сайтов (embed Telegram, telegra.ph) — свой узел контента.
- **Контакты** (`ContactExtractor`, единственное место): e-mail (и «name (at) domain»), Telegram (@name в посте; на веб-странице — только
  рядом со словом Telegram, там @name бывает хэндлом другой сети), t.me-ссылки (бот — ссылка-«Посмотреть контакт», mini-app — реклама),
  телефоны через libphonenumber (валидность по стране BY/RU/KZ, E.164; 8-800 и прочие горячие линии — не контакт), LinkedIn, WhatsApp.
  Ссылка с подписью-откликом («Откликнуться», «Apply») — контакт-ссылка, даже если страница за ней никого не называет. Хром площадки
  (её канал, support@, dmca@) и соцсети-иконки сайта отбрасываются, общие ящики (info@, request@) — в конец.
- **Модель** читает пост, скрытые ссылки и страницы (`<post>`, `<links>`, `<page>` — данные). Её контакты и URL проверяются по
  источникам: Telegram — только если его называет сам пост; адрес вакансии — только живая страница или hh из ссылок поста (не бот, не
  форма, не 404).
- **Telegram-проверка** (`TelegramContactVerifier`): @username остаётся, только если это человек (`contacts.resolveUsername`); каналы
  (футер сети каналов, канал компании), группы и несуществующие отбрасываются. Ответы — в `telegram_usernames` (30 дней), свой часовой
  бюджет, FLOOD_WAIT останавливает проверку на сколько просит Telegram; непроверяемое сейчас остаётся.
- **Какие ссылки не страницы вакансии:** соцсети, реклама, файлы, приватные и invite-ссылки Telegram; ссылка на названии технологии
  («.NET», «ASP.NET» — Telegram делает из него домен); но поддомен карьеры (`job.`, `careers.`, `hr.`) читается, даже если основной
  сайт в списке пропуска. Адрес вакансии — страница с `JobPosting` или путём вакансии раньше страницы компании.
- **Без модели не читать:** если все модели извлечения на паузе, пост остаётся в очереди без попытки, воркер постов ждёт
  (`QueuePausedException`, 2 мин; 30 мин — дневной бюджет) и не читает страницы, которые некому разобрать.
- **Перечитать** старые посты: `/reparse [id…]` в боте (без номеров — вакансии из Telegram без контактов). Если пост — единственный
  источник вакансии и модель ответила, новое чтение заменяет контакты; иначе только добавляет. `--read-link <url>` — прочитать одну
  ссылку, как из поста (страницы, маршрут, контакты), ничего не сохраняя.
- **Прокси** (`Scrape:Proxy`, прокси ShadowPrompter на хосте): сайт, до которого прямой маршрут не дошёл (соединение, DNS, TLS-сброс,
  таймаут), повторяется через прокси и остаётся на нём сутки; `Scrape:ProxyHosts` — всегда через прокси. Ответ сайта (403, капча) —
  блокировка, не повод менять маршрут. Сертификат российского УЦ (job.alfabank.ru) прокси не лечит: TLS сквозной.

### 3.2 Жёсткие фильтры (детерминированные, до LLM, с причиной отказа)
- заголовок содержит стоп-слова (junior, стажёр, frontend, QA, 1С, Java, …) или не содержит маркеров .NET/C# (в заголовке, навыках или описании);
- география и формат: офис/гибрид только в Минске; удалёнка — компании из РБ или РФ (страну даёт `area.path`: `.16.` РБ, `.113.` РФ);
  вакансии из других стран без удалёнки в РБ/РФ отбрасываются;
- английский: структурное требование hh (`languages[].degree`) или извлечённое LLM выше B1 → отказ;
- компания в чёрном списке, вакансия в архиве или закрыта, уже есть отклик.

Зарплата — не фильтр: детерминированная поправка к скору (вилка ниже ожиданий → минус, выше → плюс; курсы в конфиге).

### 3.3 Оценка (LLM, JSON Schema)
`score 0..100`, подоценки (стек, грейд, домен, формат, английский, компания), `strengths[]`, `gaps[]`, `redFlags[]`, `summary`
(2–3 предложения), `englishRequired`. Текст вакансии передаётся как данные внутри тегов, промпт явно запрещает исполнять инструкции
из него. Итоговый скор = LLM + зарплатная поправка, с ограничением 0..100; обе части видны в дашборде.

**CLI-превью.** `--score <hh URL>` читает публичную страницу через `PoliteHttp` и передаёт detached snapshot в тот же native
assessment executor (input v3), а не вызывает модель самостоятельно. Корень с `VacancyId=0` имеет отдельный `PreviewKey`; score,
стоимость и hash сохраняются перед Finish. Превью не создаёт/меняет вакансию, решение, отклик или карточку и не запускает доставку.
Диагностический score доступен даже при отказе hard filter или ещё непроверенном профиле; letter-preview требует проверенного
профиля/сохранённых фактов и прежнего maximum Application/≥9 content gate. Отсутствующие факты не создаются автоматически.
Профиль, факты, search policy, зарплата и маршруты остаются захваченными; более новая редакция кандидата не подменяет старый результат.
`--score-preview <guid>` продолжает сохранённое превью без чтения hh и повторной оплаты Score; native letter также warm-reuses
свой проверенный результат. Ctrl+C прекращает ожидание, не запрос. Это proof сохранения/reuse на synthetic provider, не замер
реального p50/p95; process/live/provider приёмка и общий релиз ещё не завершены.

### 3.4 Решение
| Условие | Действие |
|---|---|
| скор ≥ `AutoApplyThreshold` (80), hh/rabota, нет теста работодателя, лимит дня не исчерпан, автоотклик не на паузе | `AutoApply` |
| скор ≥ `ApprovalThreshold` (60) | `NeedsApproval` (для Telegram/Threads/Хабра — черновик сообщения и контакты; отправка в ЛС только кнопкой) |
| иначе | `Ignore` |

Пороги, лимиты и пользовательские переключатели автоматизации — в версионируемом документе `policy.automation` (`app_documents`).
Публикация всего агрегата, `policy_revisions` и уведомление сохраняются одной транзакцией; старая форма получает конфликт версии.
Первое чтение переносит действующие значения из `settings`, сохраняя отдельные операционные cooldown/cursor keys в прежней таблице.

### 3.5 Проверенная отправка отклика

`EmployerContentGate` завершает проверку письма и PDF до отправки. `DeliveryGateway` захватывает только текущую Pending-ревизию под
блокировкой вакансии и сохраняет `delivery_attempts` в той же транзакции. Отмена/редактирование выигрывают до захвата либо сообщают,
что отправка уже началась. SMTP/Telegram получают проверенный буфер PDF; ID/hash вложения сохраняются из выбранного пакета, а не из
последнего резюме после отправки. HeadHunter не приписывает себе локальный PDF.

Границы отправки и платных letter/resume-движков проверяются по вызовам в скомпилированных Pipeline/App/Bot/Integrations, включая
async state machines и method-group delegates (`ModuleOwnershipTests`). CLI/бот не вызывают адресуемые SMTP/Telegram/hh-адаптеры
напрямую. Self-тесты имеют отдельные API без параметра адресата; это не исключение для всего бота. Это защита конкретных границ,
не завершённая проверка всех пяти модулей и не доказательство поведения сети при отправке.

`SingleInstanceGuard` захватывает advisory lock перед migrations/recovery и проверяет соединение/lock во время работы. Потеря
владения отзывает разрешение gateway на отправку и останавливает host. Журнал отклика различает Confirmed, KnownNotSent,
OutcomeUnknown и DryRun. Подтверждённая пользователем сверка имеет отдельную отметку Reconciled и не доказывает доставку всего
исходного пакета. Переписка с рекрутерами, ответы (включая follow-up), outreach по Telegram/email и hh CLI теперь используют тот же
шлюз через `EmployerMessages`. Перед отправкой фиксируются источник/ревизия, контекст, версии профиля/фактов, проверка текста и точный
ID/hash PDF. Проверенное письмо сохраняется, пока резюме готовит отдельный durable workflow: ожидание не занимает delivery handler
и не запускает повторную платную проверку письма. Ручная сверка неизвестного исхода — `--message-reconcile`: сама ничего не отправляет
и не подтверждает доставку PDF. Остальные handoff/module/release условия отслеживаются в `docs/REFACTORING.md`.

### 3.6 Управление паузой откликов

`ApplicationBlocks` владеет captcha-паузой hh: совместимая строка `apply.blockedUntil`, отдельная версия-тумбстоун и неизменяемая
история в `application_block_revisions`. Known-not-sent receipt сохраняет блокировку и native-уведомление в транзакции результата
отправки/retry. Чтение обходит общий десятисекундный кеш; повреждение версии/значения/истории останавливает автоматическое продолжение.

Снятие использует исходный `ApplicationBlockSnapshot`, в том числе отсутствие блокировки до начала login. Новая пауза с тем же
временем не считается прежней. `ApplicationAutomationControls` объединяет версионированную политику и снятие captured-паузы в один
commit; аварийное включение паузы не требует актуальной версии captcha-блокировки. UI сохраняет исходные версии и выбор при конфликте
или неподтверждённом сохранении до явной загрузки; таймер обзора не перебазирует такое действие. `/resume` захватывает обе версии,
а CLI hh-login — версию паузы до открытия браузера. Ни один из контролов не сверяет и не повторяет неизвестную доставку работодателю.
Изолированные source/UI/receipt проверки закрыты; живые browser/owner-chat проверки и общий release пока открыты.

## 4. LLM-слой (`JobFinder.Llm`)
- `LlmRoutes`: для каждого назначения — упорядоченный список моделей; у каждой модели свои `ExtraBody` (reasoning, provider), маршрут (прямой или прокси)
  и режим structured output (`json_schema` / `json_object`). Защищённые поля запроса не переопределяются через ExtraBody.
- `ModelHealth`: у каждой модели свой breaker. 429 → пауза по `Retry-After` или экспоненциальная (15 с..15 мин); 5xx или таймаут два раза
  подряд → пауза; 400/404 на модель → длинная пауза. Ответ, не прошедший десериализацию или валидацию, — тоже ошибка модели, запрос уходит следующей.
- Каждый вызов пишется в `llm_calls` (модель, токены, стоимость из `usage.cost`, задержка, ошибка). `DailyBudgetUsd` — дневной потолок:
  после него фоновая оценка ставится на паузу, бот присылает алерт. Usage/cost пустого или обрезанного ответа записывается перед
  переключением модели, если провайдер вернул эти данные.
- Промпты лежат в `prompts/*.md` (данные, а не код); отсутствующий файл — ошибка на старте.
- JSON Schema исполняется локально до десериализации и семантической проверки. Все structured-задачи получают отдельные strict wire DTO;
  схемы генерируются нативным JsonSchemaExporter из source-generated metadata, choices/ranges принадлежат wire-полям.
  `ExtractPostTask` уже владеет типизированными входами и bindings; перенос остальных bindings в общий каталог продолжается.
  Совместимость старого persisted JSON не ослабляет проверку wire-ответов и не открывает модели управляемые приложением поля.
- Deployment Options используют native binding/validation; сервер и CLI имеют общий порядок источников. CLI проверяет нужные
  секции явно, не запуская host/background services.

## 5. Источники

### hh.ru / rabota.by (`HeadHunter`)
- Поиск: для каждого профиля поиска из конфига (текст, `search_field=name`, `area`, `work_format`) — `order_by=publication_time`,
  `items_on_page=100`, `search_period` дней. Проход раз в 45±15 минут, кроме ночи (`QuietHours` 00:30–07:00): страница 0 каждого
  профиля, следующая, только пока на текущей есть новые id (всё старше собрано прошлыми проходами).
  Окно 30 дней (срок жизни вакансии на hh): уже известные id ничего не стоят, а окно в 3 дня теряло все открытые вакансии старше.
- Лимиты сайта (`PoliteHttp`, общие для всех задач, читающих hh): rabota.by за DDoS-Guard, клиент без его JavaScript-проверки
  получает небольшой лимит с одного адреса, дальше 403. Поэтому весь трафик семейства hh под бюджетом: 6 запросов за 10 минут,
  24 в час, 250 в сутки (скользящие окна `System.Threading.RateLimiting`), 12–30 с между запросами. Приоритеты: фон (догрузка
  вакансий откликов, ночной сбор компаний) берёт не больше половины бюджета и ждёт слотов, поиск и новые вакансии — остальное,
  ссылка пользователя идёт вне бюджета. Блок (403/429/капча) размыкает цепь Polly: пауза 2 часа, каждый блок подряд удваивает её
  (4, 8, 16 часов, максимум сутки); первый запрос после паузы — проба. Пауза, серия и запросы суток переживают рестарт (`settings`).
  Метрика `jobfinder_scrape_requests_total` (family, priority, outcome: ok / blocked / paused / budget) в Prometheus.
  Официальный API hh не вариант: с 15.12.2025 вакансии в нём только для приложений работодателей.
  Кроме поиска по названию — профили на языке запросов hh `NAME:(backend OR разработчик …) AND DESCRIPTION:(".NET" OR "C#")`:
  бэкенд-роли, где .NET только в описании. Проход с ≥ 10 новыми вакансиями объявляется одним сообщением; карточек на одобрение
  не больше 6 в час (`VacancyWorker.MaxApprovalCardsPerHour`), остальные ждут в `/top`, на дашборде и в дайджесте.
- Вакансии по ссылке: сообщение боту со ссылкой hh / rabota.by («Поделиться» из приложения hh), поле на странице «Вакансии» или
  `--add-vacancy` кладут id в `settings` (`hh.links.pending`, `HhLinkQueue`). `HhLinksJob` (раз в 10 минут и сразу по добавлению)
  читает страницу под сессией пользователя (настоящий браузер проходит JS-проверку DDoS-Guard, одна страница без кликов, не больше
  `AccountReadsPerDay` = 30 в сутки), иначе анонимно вне бюджета; дальше обычный поток: фильтр, оценка, автоотклик или карточка
  (отклик и так идёт браузером). Ждут ссылки, только если нет ни сессии, ни анонимного доступа (пауза); уже известная вакансия не
  читается заново, в бот уходит её состояние. Поиск и догрузки под аккаунтом не ходят никогда.
- Карточка: страница вакансии → `vacancyView.vacancyFull.vacancy` (описание, `keySkills`, `languages`, `workFormats`, зарплата, статус).
- Компании: страница `/employer/{id}` → `employerInfo` (индустрии, описание, сайт, размер) + `activeEmployerVacancyCount`.
- Отклик: Playwright, сохранённый `storageState` (`--login hh` на хосте). Все селекторы вынесены в конфиг (`HeadHunter:Selectors`), чтобы
  чинить поломки без пересборки. Скриншот при каждой ошибке; капча или протухшая сессия ставят ApplyWorker на паузу и шлют алерт.
- История откликов (`HhNegotiationsJob`, раз в час, под сессией): страница «Отклики» → `hh_responses` (состояние, просмотр, чат, даты).
  Отклик пользователя на сайте присоединяется к собранной вакансии (`HhHistory.Link`: External-отклик со стадией hh). Вакансия с таким
  откликом оценивается полностью, но не встаёт в очередь (решение None, без письма и карточки): она нужна разбору отказов. Вакансии
  откликов, которых поиск не собрал (закрытые, старые, другой регион), догружаются по id, по 3 за проход, и оцениваются даже закрытыми.
  `HhResponseBackfillSources` хранит отрицательный кеш в БД: 404/410 — 7 дней, ошибка формата — час; изменения данных отклика снимают
  подавление, обычный timestamp синхронизации — нет. Приоритет Low и бюджеты чтения сохраняются.
  Чат каждого отклика читается один раз целиком (по 5 за проход, сначала отказы и приглашения): только история, без автоответов.
  `HhChatHistorySources` атомарно публикует события, маркер, прогресс и уведомление с native-командой. Две отдельные неудачные
  попытки завершают импорт с предупреждением; счётчик хранится в БД. Публикация проверяет захваченный источник и отказывается
  при активном входящем анализе; приём нового сырого сообщения использует ту же блокировку отклика. Стадия и last-inbound не меняются.
- Блокировка: 403/429/капча ставят на паузу всё семейство сайтов hh на 2 часа (`PoliteHttp`, пауза хранится в `settings` и переживает
  рестарт, cookies сбора сбрасываются), об этом одно уведомление с временем окончания паузы. Пока пауза, чтение чатов браузером тоже
  ждёт. Чат с отказом закрыт для ввода: для чтения достаточно сообщений (`HhChat.ReadAsync`), первое из них («Отклик на вакансию /
  Без сопроводительного письма») говорит, было ли письмо.

Квоты и паузы источника принадлежат `ScrapeStateStore`, не общему кешу настроек. PostgreSQL сериализует admission каждой direct/proxy
попытки для семейства; актуальное окно проверяется до сети, поэтому CLI и сервер не перезаписывают запросы друг друга. Background
имеет отдельную долю, High не расходует счётчики, но всегда ждёт действующую паузу. Локальные standard rate limiters/pacing и Polly
сохранены; ledger — окончательная граница допуска. Legacy pause/budget читаются без записи, затем переводятся в атомарную owned
проекцию; повреждённые значения не означают пустую квоту. Block/recovery с native-уведомлением сохраняются вместе, успешный старый
запрос не снимает новую паузу. Ожидание квоты ограничено `maxWait` и cancellation, отдельно от timeout HTTP. Interrupted admission
может консервативно занять квоту без запроса; global pacing/exactly-once HTTP и production speedup этим не доказаны.

### Telegram
- `--login-telegram`: код подтверждения читается из консоли или из файла `data/telegram.code`; 2FA-пароль берётся из конфига. Сессия —
  в `telegram_sessions` (конструктор WTelegramClient `byte[]` + колбэк: библиотека отдаёт сессию синхронно под своими блокировками,
  `SessionWriter` пишет её в БД в фоне, последняя версия побеждает, сбой записи повторяется, при остановке запись дожидается).
  Позиция апдейтов (`UpdateManager.State`) — документ `telegram.updates`, раз в 5 минут и при остановке.
- Список каналов — таблица `telegram_channels` (seed из `config/telegram-channels.json`). Статусы `Proposed → Approved → Joined`; вступаем
  только в `Approved`, с паузой 40–120 с, FLOOD_WAIT соблюдается. После вступления: mute навсегда, архив, папка «Jobs».
  Чаты, вручную добавленные в папку «Jobs», тоже подхватываются.
- Одобрение/отклонение принадлежат `ChannelDecisions`: UI сохраняет показанную идентичность/статус/DecisionRevision,
  бот — ID сохранённой подборки, а не «все Proposed на момент нажатия». Seed и карточки по ≤ 20 каналов, решения/история
  и native-уведомления сохраняются атомарно. Новые предложения не попадают под старую кнопку; повтор не отменяет поздний отказ.
  Конфликт сохраняет исходный выбор до явного обновления. Счётчики/заголовок не меняют версию решения; устаревший результат
  синхронизации не затирает статус. Подписка выполняется только `ChannelMembershipWorkflow`: Resolve → Join → Mute →
  Archive → Folder → ReadHistory → Publish. Root фиксирует источник/ревизию, аккаунт, входные данные и хеши; каждый
  mutating RPC имеет отдельную сохранённую попытку. Gateway повторно проверяет владение, аккаунт, источник и claim
  непосредственно перед RPC; для папки — после её чтения. `INVITE_REQUEST_SENT` означает заявку, а не Joined.
  Полный набор связанных receipts, история, статус канала и команды обработки постов публикуются атомарно.
  Потерянный ответ, отмена наблюдения или падение с Sending требуют сверки, без автоматического повтора.
- Импорт папки и сообщение об утрате доступа принадлежат `ChannelCollectionSources`, с исходным аккаунтом и witness
  канала. Отклонённый/native-owned канал не импортируется в обход root. Мониторинг — производная память с reload,
  не бизнес-состояние. Catch-up читает историю; `PostProcessingRequests` владеет приёмом/дедупликацией постов и
  high-water cursor. Контактный backfill имеет отдельного владельца совместимого progress key и CAS завершения.
  Эти read-only чтения не объявляются новым durable MTProto executor или exactly-once чтением.
- Проверенная `--channel-membership-reconcile <guid> --attempt <guid> --applied|--not-applied --evidence "…"`
  сохраняет свидетельство без MTProto и без продолжения. Для новой подготовки требуется отдельное одобрение.
  Изолированные process-kill проверки описаны в `docs/UBUNTU-ACCEPTANCE.md`; live Telegram и production не проверены.
- Префильтр (regex по .NET/C# + маркеры вакансии) отсекает большую часть сообщений ещё до LLM.

### Threads
- `ThreadsApiClient`: `GET /keyword_search?q=…&search_type=RECENT`, ответ — `POST /me/threads` (`reply_to_id`) + `/threads_publish`.
- `ThreadsBrowserClient`: `threads.com/search?q=…&filter=recent` под сохранённой сессией; ответ — через UI поста.
- Вакансии идут в общий конвейер `raw_posts`; поиск аудитории — отдельные ключевые слова → LLM-классификация (HR / лид / тех / найм;
  стоит ли комментировать) → 3 варианта → публикация (или бот без `AutoPublish`). Лимиты: N комментариев в день, не больше одного комментария автору за 7 дней, посты не старше 48 ч.
- Платная подготовка комментария принадлежит `Modules/Engagement/CommentPreparationWorkflow`: `CommentPlanner` только создаёт
  запрос и ждёт. Draft/check/rewrite сохраняют контрольные точки вместе со следующей командой; проверка не повторяет сохранённый
  платный draft. Операция фиксирует профиль, пост, примеры промпта, LLM-политику и recipe. Выживший набор вариантов проверяется
  заново, включая обязательный вопрос. `--comment-test` / `--comment-refresh` требуют сервер-consumer, а не запускают второй.
  `CommentSources` фиксирует допуск, резерв лимита, профиль и политику; `CommentSourceWorkflow` сохраняет ссылку на child-запрос
  вместе с его командой. Завершение child атомарно будит parent; оплаченная работа не удерживает source-handler. Финальный
  `comment_drafts`, замена прежнего Pending-черновика и карточки/редактирование клавиатуры сохраняются атомарно.
  `CommentDecisions` проверяет захваченную ревизию: конфликт сохраняет текст в UI, бот использует версию своего запроса.
  Доставка — `PrepareCommentDelivery` → `DispatchCommentDelivery`: API-контейнер ещё не публикация; попытка и pacing сохраняются
  до эффекта. Неизвестный исход не повторяется: `--comment-reconcile` записывает проверенный результат без отправки. Живые страницы
  Meta, production cutover и общие release gates ещё требуют отдельной верификации.

## 6. Данные (PostgreSQL, EF Core)

Контактами компании владеет `Modules/Hiring/ContactSources`: наблюдения повышают ревизию, ручное добавление и исключение
сохраняются вместе с native-уведомлением. Кнопка исключения передаёт snapshot показанного контакта; устаревшая версия не
перебазируется автоматически. Исключение выставляет `retired_at`, не удаляя адрес и историю аутрича. Повторное обнаружение
не оживляет контакт, подготовка новых обращений через реестр его исключает, а входящая переписка сохраняет привязку.
Допуск сообщения и исключение сериализуются shared/exclusive блокировкой контакта; связанная отправка/неизвестный исход/
история доставки запрещают исключение. Независимый маршрут первого отклика по `VacancyContact` этим действием не изменяется.

Очисткой владеет `Maintenance/OperationalRetention`: ограниченные батчи удаляют только чистые необработанные noise-посты и
неиспользуемые завершённые диагностические job runs старше 30 дней (не дайджесты). Все native/business-истории, уведомления,
попытки доставки, edit-tombstones, курсоры, артефакты и история оплаты LLM сохраняются бессрочно. Отсутствие метаданных не
доказывает отсутствие оплаты или отправки. Running-задачи не объявляются прерванными по возрасту: это делает только
`StartupRecovery` после получения владения сервером. Автоматического удаления/архивации native-истории нет.

| `job_runs`, `llm_calls` | здоровье джобов и расход LLM |
| `app_documents` | состояние одним куском, JSON по имени с версией (`IDocumentStore`): `candidate.profile` (+ `.previous` до реимпорта), `candidate.facts`, `browser.<site>` (storage state Playwright), `telegram.updates`. Колонка `json`, не `jsonb`: документ читается целиком, текст хранится как записан, а `\u0000` из local storage сайта jsonb не принимает. Чтение — `DocumentCache<T>`: одна короткая выборка версии, текст и разбор только после записи (из любого процесса) |
| `candidate_revisions` | неизменяемая история профиля и фактов: ключ, версия, точный JSON, actor, момент публикации. Candidate owner сохраняет документ, историю, предыдущий профиль при импорте и notification одной транзакцией; устаревшая форма не перезаписывает новую версию |
| `telegram_sessions` | сессия MTProto аккаунта (bytea, зашифрована api_hash самой WTelegramClient) |
| `data_protection_keys` | ключи антифоржери и схем Blazor (`PersistKeysToDbContext`) |
| `application_events` | история отклика: смена стадии, входящее/исходящее сообщение, напоминание, заметка; черновик ответа и его статус; `external_id` — дедуп входящих |
| `tailored_resumes` | резюме под вакансию: язык, содержимое (jsonb), PDF, покрытые ATS-ключи и пробелы, исправления проверки фактов, отчёт (`report_json`: план требований, рецензия, страницы, вёрстка), модель и цена |
| `stories` | банк историй STAR + вывод; подтверждённые — факты для резюме и писем |
| `interviews` | этапы интервью: тип, время, длительность, пакет подготовки (jsonb + PDF), напоминание, дебриф |
| `company_contacts` | люди и адреса компаний: Telegram, e-mail, LinkedIn, телефон; источник, сколько раз встречался |
| `outreaches` | черновики и отправленные сообщения контактам компаний |
| `offers` | офферы: сумма, валюта, gross/net, net USD (код), разбор модели (jsonb) |
| `offer_preparation_requests` | замороженные входы/маршруты/recipe, стадия Analyze → Publish, сохранённый разбор/hash и итоговый offer ID |
| `mock_sessions` | тренировки интервью: вопросы, ответы, оценки, итог |

## 9. Карьерный контур: после отклика

```
отклик отправлен ─→ application.stage = Sent (+ событие с письмом)
      │
      ├─ ответы: Telegram ЛС (MTProto, по user id / @username) · почта IMAP (In-Reply-To/References, адрес, домен компании,
      │          письма hh) · статусы и непрочитанные чаты hh (страница «Отклики» под сессией) · кнопки в боте/дашборде
      │     └→ ReplyService: событие → LLM (приглашение / вопрос / отказ / оффер + время) → стадия → DialoguePolicy:
      │        рутина по подтверждённым фактам уходит сама (чат hh, ЛС, почта), остальное — карточка с черновиком и причиной
      ├─ стадия HR / тех / финал → Interview + PrepareInterview атомарно → native preparation → PDF и карточка в бот
      │     └→ за 60 мин экран «за 10 минут» · через 2 ч после конца «как прошло?» → дебриф (вопросы, выводы, благодарность)
      ├─ 5 рабочих дней тишины → черновик напоминания · ещё 7 дней → NoResponse
      ├─ скор ≥ 80 → OutreachService: лучший контакт компании (пост → hh → поиск Telegram → поиск LinkedIn ≤ 10/день),
      │     заметка ≤ 300 знаков, не чаще раза в неделю на компанию; LinkedIn — только ссылка и текст
      │     OutreachScans сохраняет резерв/backoff в PostgreSQL: сбой не исключает вакансию навсегда; новые исходные данные снимают ожидание
      ├─ рекрутер компании (`company_contacts`): из поста, из текста вакансии (@username / t.me/…, только если Telegram говорит, что
      │     это человек, не канал и не бот), от пользователя (бот: ссылка на вакансию + @username или «#id @username»; страница
      │     вакансии → «Рекрутер в Telegram» → «Привязать»). Его ЛС в Telegram, если отсюда ему не писали, идут в последний отклик
      │     на эту компанию только черновиком: этот чат пользователь ведёт сам
      ├─ переписка с рекрутером (`RecruiterChatService`, страница вакансии → «✈️ Рекрутер в Telegram», бот: «✈️ Написать»):
      │     черновик под ситуацию (отклика нет / ждём / тишина / написали без ответа (короткое напоминание) / переписка / интервью /
      │     отказ) с перепиской отклика в контексте, через общий `LetterWriter` (см. «Письма работодателю» ниже). «🧼 С чистого листа» (после отказа по
      │     умолчанию): модель не получает прошлый отклик вовсе; отправка после закрытого отклика — новая попытка в воронке.
      │     Отправка только кнопкой, резюме под вакансию по умолчанию к первому слову; без отклика сообщение и есть отклик
      │     (TelegramDm, воронка, вакансия Applied), с откликом (hh) ложится в его историю + sent-outreach, чтобы ответы пришли туда же.
      │     Чат с человеком читается через MTProto целиком (свои сообщения с телефона тоже): по кнопке «🔄 Переписка», раз в 30 минут
      │     для откликов за 45 дней и перед разбором каждого входящего; id событий те же, что у живых входящих ({userId}/{msgId}),
      │     отправленное отсюда сопоставляется только по точному непустому тексту с единственным событием; это не доказательство
      │     доставки PDF; история старше отклика больше чем на 2 недели не берётся
      └─ оффер → OfferAdvisor (producer) → OfferPreparationWorkflow (Analyze → Publish): условия, net USD и перцентиль рынка,
            сравнение с другими офферами, риски, вопросы, цель / нижняя граница / текст контрпредложения
```

**Входящая почта.** `EmailInboxJob` захватывает курсор, читает IMAP read-only и передаёт пакет в `EmailInboxSources`. Курсор,
preimage/receipt и допуск native-разбора коммитятся вместе. Курсор привязан к серверу/логину/INBOX и UIDVALIDITY; смена эпохи
перечитывает ящик ограниченными пакетами, не повторяя сохранённый разбор того же RFC Message-ID и не разрешая автоматические
ответы восстановленной истории. Отсутствующий Message-ID получает identity аккаунта/эпохи/UID. Старый `email.lastUid` сохраняется,
но не доказывает identity. Указатель из письма hh сохраняет запрос синхронизации до успешной публикации нового чтения hh, а не
до transient wake-up. Живой IMAP/TLS и приёмка ящика остаются release-проверками.

**История Telegram.** `RecruiterChatService` захватывает исходный witness до чтения MTProto; `TelegramChatHistorySources` владеет
записью истории. События, revisions/времена отклика и native-уведомление публикуются одной транзакцией. Pending/Sending/неизвестная
доставка, активный входящий разбор, изменившийся контакт/источник или другой peer не допускают публикацию. Исторический внешний
отклик остаётся External: история не запускает модель/ответ, не примиряет неизвестную отправку и не подтверждает доставку резюме.

**Интерактивные истории.** `StoryBank` не вызывает модель и не сохраняет диалог самостоятельно. `StorySources` атомарно публикует
вопросы/ответы вместе с native-уведомлениями. Четвёртый ответ и исходный контекст (версии профиля/фактов, текст резюме, четыре вопроса,
все ответы и Coach-маршрут/recipe) сохраняются с корнем и командой до возврата обработчика бота. `StoryPreparationWorkflow` исполняет
Draft → Publish: платный STAR-черновик с hash и следующая команда коммитятся вместе; готовый диалог, полная карточка с предупреждением
о неподтверждённых числах и завершение корня — тоже вместе. Ошибка публикации не повторяет модель. Сам черновик ещё не факт:
подтверждение проверяет исходный native-корень и точный текст, сохраняет provenance в `Story.PreparationRequestId` и immutable history.
Переписывание удерживает предыдущий черновик, но запрещает подтвердить его во время ожидания; старые кнопки не действуют на новое состояние.
Skip/Stop сравнивают захваченный диалог, отменяют только его работу и сохраняют raw/paid evidence. Сбор фактов доступен и до проверки
профиля для отправки работодателям. Реальный процесс/провайдер/чат владельца остаются отдельными release-проверками.

Разбор оффера не держит обработчик бота до ответа модели. `OfferPreparationRequests` атомарно сохраняет исходный текст и waiting-диалог,
корень, команду и уведомление; профиль/версии фактов, открытые отклики, рынок, сравнения, коэффициенты пересчёта и максимальный Resume-маршрут
заморожены до платного анализа. Результат с hash сохраняется вместе с командой публикации. `OfferSources` проверяет тот же witness;
оффер, переход воронки, compare-clear исходного диалога, полная карточка переговоров и завершение корня коммитятся вместе.
Ошибка публикации не повторяет модель. `/stop` отменяет только захваченный waiting-диалог/корень, не новый диалог; поздний результат не публикуется.
Контрпредложение остаётся текстом для копирования, не автоматической отправкой. Смерть процесса до paid-checkpoint может повторить
незавершённый вызов: это не exactly-once провайдера и не замер реального ускорения.

- **Подготовка к интервью** (`InterviewPreparationWorkflow`, `CopilotRules`, маршрут `Interview`: максимальный reasoning effort). Не исследование, а речь.
  Единственный executor — Wolverine/PostgreSQL: capture → plan → answers → print → publish. `InterviewPrep` и `--interview` только
  публикуют запрос и ждут; `InterviewWorker` ограниченно импортирует legacy-строки. Источник, revision/owner, операция с замороженными
  входами и следующий command сохраняются вместе. Scheduling из бота/UI, входящих приглашений и hh-истории присоединяется к source owner
  через `InterviewTransitions`, без параллельной генерации. Конфликтные формы сохраняют ввод и captured witness до явной перезагрузки.
  Проход 1 (`interview_plan`): по вакансии, переписке, каталогу доказанного опыта (S — истории, A — достижения, E — места работы),
  фактам, рынку и прошлым этапам: что реально важно (приоритет, уровень кандидата, основание: confirmed / likely / speculative), shortlist
  вопросов (6 обязательных под компанию: о себе, почему компания, почему роль, почему вас, первые шаги, зарплата; плюс до 12 по приоритету; общие HR-вопросы живут в документе «HR-ответы») с одним реальным кейсом на вопрос,
  пробелы (что рядом в опыте, что повторить, как сказать), вопросы работодателю (обязательно / если останется время), переговоры, риски;
  справка о компании только как опора. Проход 2 (`interview_answer`, по 4 вопроса параллельно, уровень рассуждения по типу вопроса): речь от первого лица на 15, 30 и 60 секунд,
  куда копнут (уточнения со своим началом и ответом), чего не говорить, что сверить. `SpokenStyle` кодом отсекает заметки для себя,
  определения вместо ответа, самоуничижение (кроме подтверждённого пробела), канцелярит, списки и стек, длину не по времени; непрошедший
  ответ переписывается один раз. Guardrail `requiresApproval`: вопрос о глубине без доказанного кейса, выведенные эпизоды (verify без
  шума), переговоры, пробел, просьба модели. Экран «за 10 минут» собирается кодом из самих ответов. Дашборд `/interviews/{id}`: подготовка,
  «за 10 минут», заучивание карточками (знаю / повторить, в `settings`); бот: «Прогнать мои ответы» (вопросы из подготовки, эталон —
  подготовленный ответ, оценка 4+ отмечает выученным).
- **HR-ответы** (`HrPlaybookService`, `HrPlaybookJob`, дашборд `/hr`): банк из 34 HR-вопросов (`prompts/hr_bank.json`: зачем спрашивают,
  как отвечать, как не надо; честная редакция без советов врать) отвечается один раз из профиля, фактов, историй и реального состояния
  поиска (`hr_answer`, уровень рассуждения по вопросу, см. ниже) в том же формате речи и с теми же проверками, что подготовка к интервью. Вопросы под компанию
  (о себе, почему вы, почему к нам, первые шаги, деньги) заново готовит каждая подготовка к интервью, здесь их общий вариант. Личные
  вопросы, деньги и ответы без нужного факта (хобби, что изучаете, переработки, командировки: страница «Факты») ждут проверки.
  Собирается сам, если документа нет, и по кнопке «Пересобрать»; заучивание карточками и прогон в боте.
  `HrPlaybookService`/`HrPlaybookJob` только ставят запрос: `HrPlaybookWorkflow` сохраняет Build → Publish в PostgreSQL.
  Исходные профиль/факты, банк, истории, воронка, дата, policy/routes и recipe заморожены; шесть параллельных ответов
  используют отдельные checkpoints `GeneratedAnswers`. После сбоя модели готовые ответы переиспользуются; публикация
  сохранённого документа не вызывает модель. Новый запрос запрещает позднему старому результату заменить документ.
  Известный сбой записи платного ответа сохраняет доступный сырой partial-result и останавливает автоматический повтор;
  это не гарантия exactly-once платного вызова. `HrPlaybookSources` атомарно публикует документ/owner/флаг/уведомление,
  а ввод позиции — с исходной версией фактов, историей кандидата и новым запросом. Конфликт сохраняет текст до явного
  обновления; generic settings не пишут эти ключи. Реальные provider/process-kill/HR-browser проверки остаются release-gates.
  `LearningProgressSources` владеет совместимыми `settings` (`hr` / `interview.<id>`: `.progress`, `.approved`, `.learning`)
  и неизменяемой историей `learning_progress_revisions`. Изменение, история и native-уведомление атомарны. Разные вопросы
  объединяются под блокировкой области; устаревшая версия того же вопроса и устаревший полный сброс отвергаются.
  Интерфейс сохраняет исходную версию и желаемую правку до явного обновления и отдельного повторного применения;
  карточка не исчезает при отказе. Сброс заучивания сохраняет проверки текста ответов. Прогон захватывает версию отметки
  до разбора моделью. `MockSources` атомарно публикует сессию/историю, диалог и отметку обучения; `MockPreparationWorkflow`
  сохраняет результат вопросов/разбора/итога до публикации. Последний разбор ставит отдельный итог в очередь в той же транзакции,
  без ожидания модели внутри обработчика. `MockInterviews` только публикует запросы; `/stop` и кнопки проверяют исходную версию,
  поэтому старый вопрос не закрывает новую тренировку. Реальные process-kill/browser/owner-chat/provider-проверки остаются release-gates.
- **Уровни рассуждения, память ответов, частичная пересборка** (общие для подготовки и HR-ответов):
  - Уровень по типу вопроса (`CopilotRules.PurposeFor`): глубина (`technical_depth`) → маршрут `Interview` (xhigh), техника, system
    design, код → `InterviewHigh`, поведение, мотивация, деньги, «о себе» → `InterviewMedium`, формальности → `InterviewLow`;
    `effort` в `hr_bank.json` переопределяет. План интервью всегда на `Interview`.
  - Каждый сгенерированный ответ (и план) лежит в `generated_answers` (`GeneratedAnswers`: L1 в памяти процесса на 30 минут с
    single-flight по ключу → L2 PostgreSQL `PgGeneratedAnswerStore` → модель). Ключ версионирован: вопрос, версия промпта, версия
    схемы ответа, отпечаток маршрута (модели, effort, лимиты), профиль, каталог историй, вакансия и переписка (для интервью). Строка
    хранит ключи фактов, которые ответ реально использовал (`usedFacts` + объявленные в банке + `hr_{id}`), и их хэш: ответ берётся
    повторно, только пока эти факты не менялись. Смена одного факта пересобирает только зависящие от него ответы. Модель, purpose,
    версия промпта, стоимость и `hits` в строке дают экономию (`SavedUsdAsync`, шапка `/hr`) и метрику `jobfinder.answers`
    (`source` = memory / store / generated). Redis не нужен: переживает рестарты и входит в ежедневный бэкап.
  - Уровень доказанности ответа (`evidenceLevel`): verified / derived / personal_unknown / unsupported. Личное, чего нет в фактах
    (статус, переработки, командировки, выход), не выдумывается: вместо речи карточка «нужна ваша позиция» с вариантами (`options`
    в банке или `positionOptions` модели) и полем «своими словами»; выбор сохраняется подтверждённым фактом (объявленным или `hr_{id}`),
    и пересобирается только этот ответ. Сохранение на странице «Факты» тоже ставит пересборку HR.
  - Проверка: `blocker` (решение за вами: позиция, деньги, пробел, глубина без доказательств, речь не прошла) показывается рамкой;
    `review` (эпизоды, выведенные из опыта) свёрнут в «глянуть». Отметка «проверено» привязана к отпечатку текста ответа: переписанный
    ответ снова требует проверки.
- **Письма работодателю** (`LetterWriter`, промпт `recruiter_dm`; первое слово — маршрут `Application`, xhigh, дальше — `ReplyDeep`):
  генерация исполняется только в нативном Hiring workflow: две сохраняемые дорожки Drafting → Reviewing на раунд, до четырёх
  раундов. `LetterWriter` публикует запрос/ждёт результат; после сбоя проверки платный черновик не пишется заново. Оценка вакансии
  сохраняет зависимость от письма и освобождает handler до продолжения. Чистые 10/10 завершают сразу, 9/10 дают второй дорожке
  один фиксированный 20-секундный срок; поздний результат не заменяет выбранный. Точный контекст/дата/версии определяют warm reuse,
  явная регенерация создаёт новую генерацию. Нативные очереди черновика/проверки разделены; качество и максимальный effort сохранены.
  Заметки LinkedIn, автоматические и по явно выбранному контакту, используют тот же executor с `LetterChannel.LinkedIn` и
  захваченными profile/facts. Компактная строка вакансии сохраняет полную ссылку; лимит 300 включает всё сообщение.
  Текст после проверки не обрезается: превышение запрещает публикацию. Только этому каналу не требуется обычный минимум
  250 символов тела; цитатная опора, независимый checklist >= 9 и максимум Application остаются обязательными.

## 10. Хранение и бэкапы

- Диск Docker Desktop (образы и том `pgdata` с базой) — на NVMe `E:\Docker\wsl` (настройка Docker Desktop `CustomWslDistroDir`);
  системный C: не используется: его переполнение уже однажды остановило Docker и базу.

  — другой физический диск, HDD), хранятся 14 дней. Восстановление: `pg_restore --clean --if-exists -h 127.0.0.1 -p 5433 -U jobfinder -d jobfinder <файл>`.
- Сессии Telegram и браузеров, профиль, факты и ключи дашборда — в БД, т. е. в ежедневном бэкапе. В `./data` (проект на E:) —
  только производные файлы: PDF резюме под вакансию и пакетов интервью, скриншоты, отладочные дампы; `./profile` — исходное резюме.
- Файлы старой раскладки (`profile/profile.json`, `profile/facts.json`, `data/telegram.session`, `data/telegram.updates.json`,
  `data/browser/*.json`, `data/keys/*.xml`) переносятся в БД один раз при старте сервера или `--migrate` (`FileStateImport`): только
  если в БД под этим именем ничего нет (БД всегда главнее), сессия Telegram сначала открывается api_hash из конфига. Перенесённый файл
  переименовывается в `*.imported` (резервная копия, её никто не читает); неоткрывшийся остаётся на месте до следующего старта.

## 7. Безопасность и надёжность
- Дашборд слушает только `127.0.0.1`; бот отвечает только `Bot:OwnerUserId`.
- Секреты — в `config/appsettings.Development.json` (gitignored), `config/appsettings.json` содержит только плейсхолдеры.
- Внешний текст (вакансии, посты) в промптах — данные, не инструкции.
- Автоматические действия от имени пользователя (отклик, комментарий, сообщение в ЛС, вступление в канал) ограничены лимитами и
  паузами, и каждое пишется в БД с результатом.
- Любая ошибка джоба пишется в `job_runs`, в логи и (для важных) в бот; ни одно исключение не останавливает хост.
