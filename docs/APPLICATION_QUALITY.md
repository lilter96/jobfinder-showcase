# Проверка качества откликов

## Причины исходной проблемы

Проверка истории `@CodeVal` (вакансия #371, отклик #128) обнаружила одну строку из 403 символов: приветствие, общий интерес,
опыт и шаблонное завершение без названия вакансии и ссылки. Результат проекта не был конкретизирован. В исходном PDF
названия трёх работодателей находились на первой странице, а опыт последнего продолжался на второй.

Исправление не ограничивается заменой промпта. Замечания раньше не переживали сохранение письма; одобрение могло отправить
его без повторной проверки. Наличие любой рецензии считалось достаточным для PDF, даже при низкой оценке или ошибках макета.
Сбой рецензента мог пропустить письмо; ошибка генерации PDF заменяла его исходным непроверенным файлом.
Дополнительно у резервных моделей маршрутов `Application`/`Resume` был выключен reasoning, хотя основной маршрут работал с xhigh.
Теперь все модели этих маршрутов используют максимальный поддерживаемый уровень (`max` для DeepSeek, `xhigh` для GLM/OpenAI).
Независимая проверка первого сообщения тоже идёт через `Application`, а не через более короткий `ReplyDeep`: иначе таймаут рецензента
переключал его на резервную модель без reasoning. Все каналы отправляют именно проверенную строку, включая случай отсутствующего текста в очереди.
Поддерживаемые уровни сверены с метаданными [OpenRouter Models API](https://openrouter.ai/docs/api/api-reference/models/get-models);
семантика параметров описана в [Reasoning Tokens](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

## Инварианты отправки

- Первое сообщение в Telegram/e-mail называет точную вакансию, компанию и ссылку. Для hh контекст уже задан карточкой отклика.
- Текст состоит из приветствия, коротких абзацев, одного доказанного кейса и следующего шага; не является перечнем навыков.
- Независимый рецензент проверяет утверждения по цитатам из профиля/фактов. Оценка рассчитывается кодом по чек-листу.
- Ни одобрение, ни фоновая отправка не пропускают письмо ниже 9/10 или с замечаниями. Изменение текста/входов отменяет кеш проверки.
- PDF должен иметь оценку ≥ 9, не иметь оставшихся нарушений фактов/ключей и макета, содержать извлекаемый текст целиком.
- SHA-256 связывает отчёт с файлом. Перед вложением PDF проверяется повторно; нет тихого fallback на исходное резюме.
- Исторические отправленные тексты не переписываются: проверка должна сохранять достоверность истории общения.

## ATS: основания и ограничения

[Greenhouse: причины неудачного разбора](https://support.greenhouse.io/hc/en-us/articles/200989175-Unsuccessful-resume-parse)
указывает на изображения вместо текста, таблицы, колонки, текстовые блоки/колонтитулы с контактами, неясные разделы и файлы
больше 2,5 MB. Отсюда выбран простой одноколоночный текстовый PDF с контактами в теле документа, обычными заголовками и
проверкой размера. Юридические суффиксы работодателей не добавляются, если их нет в источнике.

Тестирование чтения PDF не является сертификацией всеми ATS. PdfPig проверяет порядок и полноту текста; дополнительно
живые документы прочитаны PyMuPDF и просмотрены визуально. Настоящего доступа к импортёрам всех работодателей нет.
9/10 — внутренний чек-лист качества текста, а не прогноз ответа HR и не универсальный «ATS score».

## Скорость без снижения effort

Письма: два независимых черновика, победитель 10/10 завершает круг, вариант ≥ 9 оставляет 20 секунд другим; проигравшие
запросы отменяются. Пакет обрабатывает до пяти вакансий, правки карточек сериализуются. Спекулятивные запросы могут стоить
дороже одного вызова; отмена не гарантирует отсутствие тарификации у провайдера.

Резюме: исправления, которые может сделать код, больше не вызывают дополнительную генерацию до рецензии; замечания
переходят в следующую доработку лучшей версии. До двух разных вакансий одновременно, одна генерация для одного ID.
Профиль, факты, истории, вакансия, промпты и маршрут определяют актуальность сохранённого PDF.
При `--application-check --fresh` независимые письмо и PDF готовятся одновременно, а не последовательно; проверка старого плохого письма
по-прежнему останавливается до затрат на PDF. Отправка этим режимом не выполняется.

## Верификация

`dotnet build JobFinder.slnx` — без предупреждений. `dotnet test --solution JobFinder.slnx` — включая реальный PostgreSQL.
Регрессии покрывают сохранение отчёта, отказ одобрения плохого письма, недоступного рецензента, отсутствие доказанных claims,
изменение текста/контекста, подмену PDF, низкую оценку, неполный чек-лист, пропущенный текст и разрывы страниц.

`--application-check <id>` проверяет сохранённое письмо и вложение без отправки работодателю; отрицательный результат
возвращает ненулевой код. `--letter <id>` показывает новый черновик; `--tailor <id> --force` пересобирает документ.
`--test-llm Application` / `--test-llm Resume` проверяют каждый резервный маршрут без затрат на остальные задачи.
Оба маршрута прошли живые пробы всех трёх моделей с `max`/`xhigh`. У GLM первая проба `Application` вернула неверный результат;
повторная прошла. Такой ответ не считается успехом: в рабочем конвейере его останавливают валидация контракта и проверки качества.

Девять писем, не прошедших предыдущий пакет (26, 74, 97, 101, 110, 118, 263, 338, 339), переписаны: все получили 10/10 без замечаний,
карточки обновлены на месте. Старая запись #371 по-прежнему отклоняется preflight (код 1); история реально отправленного #128 не изменена.
782 теста проходят, пропусков нет. После развёртывания `/alive`, `/health`, `/vacancies/371` вернули 200; Playwright проверил рецензию,
чек-лист, план и отсутствие ошибок консоли, а скачанный через дашборд PDF совпал с проверенным файлом по SHA-256.
